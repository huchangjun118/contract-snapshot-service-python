# 兼容性判定规则

兼容性判定比较候选契约（candidate）与当前已批准基线（baseline）的**结构**，
给出确定性的结论：相同输入永远得到相同结论。

## 判定方向

基线 = 旧版本，候选 = 新版本。判定的是**新版本对旧调用方是否兼容**：

- 响应契约：旧调用方依赖响应结构，新版本不得删除字段或改变类型。
- 请求契约：新版本不得要求旧调用方不知道的字段。

## 变更类型

| 变更类型 | 定义 | 是否破坏 |
|---------|------|---------|
| `added` | 基线中没有、候选中新增的字段/状态码 | 否（兼容） |
| `removed` | 基线中有、候选中删除的字段/状态码 | 是（破坏） |
| `type_changed` | 同名字段的类型发生变化 | 是（破坏） |

## 具体规则

### 响应体（response body）

- 新增字段 → 兼容（调用方忽略未知字段）。
- 删除字段 → 破坏（调用方依赖该字段）。
- 字段类型变化（如 `string` → `number`、`object` → `array`）→ 破坏。

### 请求体（request body）

- 新增字段 → 兼容（调用方可以不传）。
- 删除字段 → 破坏（服务端不再接收该字段，调用方发送即多余）。
- 字段类型变化 → 破坏。

### 查询参数（query）

- 新增参数 → 兼容。
- 删除参数 → 破坏。
- 参数类型变化（参数值均为 `string`，一般不触发）→ 破坏。

### 状态码（status code）

- 新增状态码 → 兼容。
- 删除状态码 → 破坏（调用方可能依赖该状态码）。

### Content-Type

- 类型变化（如 `application/json` → `text/plain`）→ 破坏。

## 数组的处理

数组的元素结构取所有元素结构的合并，因此：

- 数组长度变化（多一个/少一个元素）**不**触发变更。
- 元素结构变化（如元素新增/删除字段、元素类型变化）触发变更。
- 空数组的元素类型为 `unknown`；`unknown` 与任何已知类型之间的差异**不**判定为
  破坏（信息不足，保守处理）。

## 混合类型（mixed）

当数组元素类型不一致时，元素类型记为 `mixed`（如 `number|string`）。

- `mixed` → 单一类型（如 `number`）：破坏（收紧了类型）。
- 单一类型 → `mixed`：破坏（放宽了类型，但调用方可能不接受新类型）。
- `mixed` → `mixed`：比较类型集合，集合变化 → 破坏。

## 判定结论

- `compatible`：无任何破坏性变更。
- `breaking`：存在至少一个破坏性变更。
- `no_baseline`：尚无已批准的基线，无法判定。
- `error`：判定过程出错（如 body 无法解析、存储不可用）。

判定结果中每个变更都包含：`path`（字段路径）、`kind`（变更类型）、
`old_type`/`new_type`（旧/新类型）、`breaking`（是否破坏）。

## 确定性保证

- 比较算法是纯函数：相同的基线结构与候选结构，永远得到相同的变更列表与结论。
- 字段路径按字典序排序输出，便于人工审查与自动化比对。
- 不依赖时间、随机数或外部状态。
